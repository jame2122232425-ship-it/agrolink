# AgroLink deployment guide

This repository is configured for a Vite frontend on Vercel, a Django API on Render, and PostgreSQL hosted by Supabase. Create the Supabase database first, deploy the Render service, then deploy the Vercel site. Replace every example domain/value with the actual deployment values.

## Deployment readiness

The repo now includes a Render Blueprint (`render.yaml`), a Vercel SPA fallback (`frontend/vercel.json`), Django static file serving through WhiteNoise, Gunicorn, and direct `DATABASE_URL` support with TLS enabled by default. The backend migrations are run as Render's release command and `/health` is configured as the service health check. All app-specific environment variables are listed in the Render Blueprint and below.

The app can use Supabase Postgres without a Supabase client SDK. However, uploaded profile, crop, livestock, report, and assistant images currently use Django local filesystem storage. Render's filesystem is ephemeral unless a persistent disk is attached, and the current app stores both public-profile and private images under that local storage. Therefore image uploads are not durable across deploys/restarts yet. Before relying on uploads in production, configure durable object storage and preserve private-image authorization, or attach a Render persistent disk and accept its single-instance constraints. Vercel hosts only the compiled frontend; do not put backend secrets there.

The frontend's API service supports `VITE_API_BASE_URL`; the existing UI also has several mock/local workflows, so deployment makes the implemented API features available but does not convert every screen into a backend-backed feature.

## 1. Create the Supabase Postgres database

1. Create a Supabase project and choose a region near the Render service.
2. In the Supabase dashboard, open **Connect** and copy the PostgreSQL connection string. Choose the **Session pooler** if the Render service cannot reach the direct endpoint over IPv6. Django persistent connections work best with the direct endpoint or session pooler; avoid transaction pooling unless you have a reason to use it.
3. Store the full connection string as Render's `DATABASE_URL`. Django parses the username, password, host, port, and database from that one variable, and requires TLS by default. Keep this string private; it contains the database password.
4. Supabase's database is the system of record. Do not use the Supabase `service_role` key as a database password; use the PostgreSQL credentials shown in the connection details.

## 2. Deploy the backend to Render

Use **New + → Blueprint** in Render and select this repository. Render reads the root `render.yaml`; if configuring a Web Service manually, use:

| Setting | Value |
|---|---|
| Root directory | `backend` |
| Runtime | Python |
| Build command | `pip install -r requirements.txt && python manage.py collectstatic --noinput` |
| Pre-deploy/release command | `python manage.py migrate --noinput` |
| Start command | `gunicorn config.wsgi:application --bind 0.0.0.0:$PORT` |
| Health check path | `/health` |

After creating the service, fill these Render environment variables. The Blueprint creates the variable slots. `DJANGO_SECRET_KEY` is generated by Render when created from the Blueprint; if setting up manually, generate a unique random Django key and do not reuse a local/example value.

| Variable | Value to enter |
|---|---|
| `DJANGO_SECRET_KEY` | Unique randomly generated secret; generated by Blueprint |
| `DJANGO_DEBUG` | `False` |
| `DJANGO_ALLOWED_HOSTS` | Render backend hostname only, e.g. `agrolink-api.onrender.com` (comma-separated if adding a custom backend domain) |
| `DATABASE_URL` | Full Supabase PostgreSQL URI from **Connect**, e.g. `postgresql://USER:PASSWORD@HOST:PORT/DATABASE?sslmode=require` |
| `CORS_ALLOWED_ORIGINS` | `https://agrolink-psi-seven.vercel.app` (add other exact frontend origins comma-separated; no trailing slash) |
| `AI_ENABLED` | `False` to deploy without live AI, or `True` to enable it |
| `AI_PROVIDER` | `gemini` |
| `AI_MOCK_MODE` | `False` for real provider calls; `True` only for labeled demo responses |
| `GEMINI_API_KEY` | Google AI Studio key when live AI is enabled; otherwise leave blank |
| `GEMINI_MODEL` | `gemini-3.5-flash-lite` or another model available to your key |
| `AI_REQUEST_TIMEOUT_SECONDS` | `30` |

`CORS_ALLOWED_ORIGINS` must include the final Vercel production origin. The Blueprint is preconfigured for `https://agrolink-psi-seven.vercel.app`; add any additional production/custom domains and Vercel preview origins only if they should use this backend. Django uses the same origins for `CSRF_TRUSTED_ORIGINS`.

After the first successful deploy, verify `https://<render-host>/health` and `https://<render-host>/api/v1/health/`. Render's release command applies migrations on deploy. Create the first admin user from the Render Shell with `python manage.py createsuperuser`.

## 3. Deploy the frontend to Vercel

Import the same Git repository in Vercel and set **Root Directory** to `frontend`.

| Setting | Value |
|---|---|
| Framework preset | Vite |
| Build command | `npm run build` |
| Output directory | `dist` |
| Install command | `npm install` (default) |

Set this Vercel project environment variable for **Production** (and Preview only if previews should use a backend):

| Variable | Value |
|---|---|
| `VITE_API_BASE_URL` | `https://<render-host>` (for example `https://agrolink-api.onrender.com`; no trailing slash) |

This value is public in the built browser bundle and must contain only the API origin, never a secret. Redeploy after changing environment variables. `frontend/vercel.json` sends client-side routes to `index.html`.

If the Vercel production domain changes, update Render's `CORS_ALLOWED_ORIGINS` to include that exact `https://...` origin (without a trailing slash), then redeploy/restart the backend.

## Environment variable inventory

There is one frontend deployment variable: `VITE_API_BASE_URL`. Backend deployment uses a single database variable, `DATABASE_URL`, plus Django security/host settings, CORS origins, and optional Gemini/AI settings listed above. The individual `POSTGRES_*` fields remain available for local development when `DATABASE_URL` is not set. Operational thresholds (`MARKET_PRICE_FRESH_DAYS`, `MARKET_PRICE_RECENT_DAYS`, and `MARKET_PRICE_AGING_DAYS`) have validated defaults in Django and do not need deployment values unless changing behavior.

Do not set `GEMINI_API_KEY`, `DATABASE_URL`, or `DJANGO_SECRET_KEY` in Vercel, frontend `.env` files, or committed files. Do not expose Supabase server credentials in the browser.

## Go-live checks

- Frontend loads at its Vercel URL; browser API requests target the Render URL.
- `GET /health` and `/api/v1/health/` return success.
- Register and sign in with a test farmer account; confirm protected API requests work.
- Confirm CORS includes the exact Vercel origin if the browser reports a cross-origin error.
- Confirm Django Admin and staff pages load on the Render host.
- Configure durable media storage before accepting important user image uploads; local Render storage can be lost.
- Keep `DJANGO_DEBUG=False`; rotate credentials if they were ever committed or shared.
